# Промт для вывода проекта из цикла «починил одно — сломал другое»

Ниже — рабочий бриф. Его можно скармливать ассистенту/себе как рамку на каждую сессию. Он построен на диагнозе, который виден прямо из `CHANGELOG.md` / `TASKS.md`.

---

## 1. Диагноз (что реально происходит)

Проект идёт по кругу не потому, что «руки кривые», а потому что выбрана **неверная стратегия позиционирования**: позиция пилюли считается набором всё разрастающихся геометрических эвристик (гейты A, B, C, D, E, F + `standaloneRow / tallIconBox / wideRow / looseRow / singleLineNode / completeBlock / closeRow / darkZone / toolbar`), каждая из которых откалибрована **по пикселям одного телефона на одной плотности**.

Признаки петли (по CHANGELOG):

- v2.10.30 → v2.10.31 → v2.10.32: три релиза подряд правят друг друга (`buttonCentered` h≥96, `toolbarCentered` w>4.5×est / h<74, `headerContentLeft`, `emptyCentered`).
- v2.10.40 вводит гейт (E) → v2.10.41 его же и откатывает («Автогид слился с Карта зарядок»).
- v2.10.42 вводит гейт (F) → v2.10.43 переделывает его начисто («пилюля = сама кнопка»).
- v2.10.35 `startLocked` ломается о собственный `view_profiles` → v2.10.36 делает «декуплинг» → v2.10.37/38/39/40 снова тюнят px-сплиты (`h<74`, `y<320`, `h≥96`, `±24px от 480`).
- «Хардгарды» в отчётах — это **не инварианты**, а снимки конкретных пикселей (`211×64 @ y1120`, `292×94`, `439×69 (54,293)`). Каждая новая эвристика обязана их не сдвинуть, поэтому любая правка сужается до «заплатки ровно под этот узел», а на соседнем экране всплывает новый дефект.

Корневая причина: **источник истины о выравнивании/отступе/шрифте берётся из геометрии рантайм-ноды, а не из XML приложения**. Приложение уже отдаёт `resource-id`, а декомпак (`view_profiles.json`, 7265 id, 6626 start-lock) уже лежит в дереве — но используется точечно, а не как основной механизм.

---

## 2. Цель

Перестать добавлять геометрические гейты и перейти на **id-first позиционирование**, где:

- Для известного `resource-id` всё (гравитация, отступ, шрифт, full-width) берётся из `view_profiles.json` — плотностно-независимо.
- Геометрические эвристики остаются **только как fallback** для серверных/программных узлов без id, и их список **фиксируется и не растёт**.
- Любое изменение проверяется **golden-набором экранов**, а не набором захардкоженных пикселей.

---

## 3. Правила работы (жёсткие, до отмены)

1. **Мораторий на новые геометрические гейты.** Ни одного нового `if (h > X && y < Y && width > est * k)`. Если очень надо — сначала доказать, что это нельзя выразить через id-профиль.
2. **Один PR = одна причина.** Если правка трогает ≥2 гейтов — разбить.
3. **Перед любой правкой** — прогон golden-набора и сохранение baseline. После — diff. В отчёте: список изменённых узлов и объяснение каждого.
4. **Никаких «хардгардов по пикселям»** в отчётах. Валидный инвариант формулируется как «пилюля X покрывает CJK-бокс Y с запасом ≥2px по каждой стороне» — проверяется скриптом, а не глазами.
5. **Регрессия ≠ изменение.** Если после правки сдвинулся узел, который не был целью — это либо баг правки, либо осознанное расширение. Осознанное расширение фиксируется в CHANGELOG как «поведение изменено намеренно, потому что …», а не молча.
6. **Не менять словарь и геометрию в одном релизе.** Разные риски, разные проверки.

## 4. Что нужно построить (по приоритету)

### Шаг 1. Golden-набор экранов (без этого всё остальное бессмысленно)
Скрипт `tools/capture_golden.sh`, который на устройстве:
- открывает фиксированный список экранов (Машина top / Машина скролл / Сервис / Сервис Deepal сетка / MY / Настройки / Настройки авто / поездка / уведомления / Исследовать / Магазин / диалоги «Отмена/Конечно» и «Вождение без ключа»);
- для каждого сохраняет: a11y-dump (`uiautomator dump`) + список окон overlay (`dumpsys window`) + скриншот;
- кладёт всё в `tools/golden/<screen>/{a11y.xml, overlays.txt, screenshot.png}`.

И `tools/diff_golden.py`, который сравнивает два прогона и печатает:
- какие id/узлы получили другой `rect`, `font`, `density` покрытия;
- для каждого изменённого узла — было/стало и на сколько процентов покрыт CJK-бокс.

Это заменит «хардгарды 11/11 побайтов» на осмысленный diff.

### Шаг 2. Инвентаризация гейтов
Таблица в `TASKS.md` (или отдельный `DESIGN.md`):

| Гейт | Условие | Для каких id реально нужен | Можно ли заменить на id-профиль? | Оставить как fallback? |
|---|---|---|---|---|
| (A) toolbarCentered | … | `titleTv`, `tab_text` | да, по `g:center` в профиле | только для id без профиля |
| (B) buttonCentered | … | `exit_button` | да (по `g:center` + fullwidth) | … |
| … | | | | |

Результат: **список гейтов сокращается**. Всё, что покрывается профилем, — удаляется из кода и заменяется одним лукапом `profileFor(viewId).gravity`.

### Шаг 3. Расширение `view_profiles.json` до «достаточного»
Сейчас 1940 id с однозначным sp. Нужно:
- добавить `fullwidth` (уже есть `fw`), `padStart` (уже есть `p`), **`gravity` из XML безусловно** (не только `center`/`left`, а `start|center|end` + `center_vertical` отдельно);
- прогнать `tools/decompile_ids.py` по **всем** layout'ам, не только тем, что дали однозначный sp; для mixed-gravity id (там где `center` встречается в одном layout и `left` в другом) — **явно помечать как `mixed`** и тогда, и только тогда, оставлять геометрический fallback;
- версионировать ассет (`view_profiles.v2.json`), чтобы обновление APK Deepal не молча ломало картину.

### Шаг 4. Переписать `computeLayout` как «решатель по приоритетам»
Псевдокод:

```
layout(node, spec):
  p = profile(spec.viewId)                    # id-first
  if p != null:
     return layoutFromProfile(node, p)        # gravity, padStart, font, fullwidth
  if isKnownServerContent(spec.text):         # только сюда — эвристики
     return layoutFromHeuristics(node, spec)
  return layoutAsLeftInline(node, spec)       # дефолт для всего остального
```

`layoutFromProfile` — детерминированный, без гейтов A–F. `layoutFromHeuristics` — **замороженный** список правил, который мы соглашаемся держать ради серверных узлов, но в него больше не добавляем.

### Шаг 5. Golden-процесс перед каждым релизом
- `git checkout` baseline → capture → сохранить;
- внести правку → capture → `diff_golden`;
- в CHANGELOG: «изменённые узлы: [список]; каждый — цель правки / осознанно расширено».

## 5. Что я хочу получить от ассистента в каждой сессии

Формат ответа:
1. **Что меняем и почему** (в терминах id-профиля, не px).
2. **Прогон golden до правки** (baseline зафиксирован).
3. **Diff после правки** (список изменённых узлов + покрытие CJK).
4. **Проверка моратория**: ни одного нового геометрического гейта (или явное обоснование исключения).
5. **Обновления CHANGELOG/TASKS**: что сделано, что отложено, какие хардгарды **переформулированы** из px в «покрытие CJK-бокса».

Формат запрещённых фраз в отчёте:
- «хардгард 211×64 @ y1120 не сдвинулся» → должно быть «плитка 211×64 покрывает свой CJK-бокс с запасом ≥2px».
- «ddy=+12» без указания центра узла → «пилюля по центру узла по вертикали (ddy = (nodeH − pillH)/2)».

## 6. Стартовое задание на ближайшую сессию

1. Написать `tools/capture_golden.sh` + `tools/diff_golden.py`.
2. Снять baseline на текущей сборке (v2.10.43).
3. Составить таблицу инвентаризации гейтов A–F + shape-классов с указанием, какой id каждый из них реально обслуживает.
4. Не менять поведение. Только инфраструктура + аудит.
5. В конце — предложить, какие гейты удаляются на следующем шаге (с доказательством по таблице).

После этого возвращаемся к фичам — но уже с сеткой безопасности, из-за которой «починил одно → сломал другое» перестаёт быть нормой.
