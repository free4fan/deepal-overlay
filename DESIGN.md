# DESIGN — позиционирование оверлеев (id-first)

## Инвариант проекта (усилен 10-21, решение пользователя)

> Оверлей работает на любом телефоне с любым разрешением тогда и только
> тогда, когда **вся логика позиционирования и размера выражена в dp/sp, а не
> в px**, а **решение не зависит от density**.

- `px` легален ровно в двух местах: **на входе** (a11y-нода отдаёт
  `boundsInScreen` в px) и **на выходе** (`WindowManager.LayoutParams` хочет
  px). Всё между ними — dp.
- Запрещены константы вида `if (h > 96 && y < 320)` в px. Допустимо
  `if (h > 42.dp)`; отступы — `24.dp`, не `54`.
- Отчёты формулируются инвариантом («плитка покрывает CJK-бокс узла с
  запасом ≥ 2dp на каждой стороне», «центр пилюли == центр узла ± 0.5dp»), а
  не «211×64 @ y1120».
- Шрифт — sp; масштаб шрифта пользователя (`fontScale`) — явно.

**Следствие для верификации**: «правильно/неправильно» определяется
**расчётом на синтетических входах при нескольких density**, а не
сопоставлением пикселей снапшота со снапшотом. Скрайншот — только для
человеческого глаза при обсуждении UX, никогда аргумент. Второй телефон не
нужен — px для любой плотности синтезируются из одного dp-представления
(первый a11y-дамп/дамп приложения).

### Почему пиксельный подход — петля (замечено 10-19 → зафиксировано 10-21)

- Гейты (A)–(F) и shape-классы откалиброваны на `density=2.25`
  (`y<320`, `h<74`, `96≤h<120`, `x≤60`, `0.83·sw`, `±24px` от центра 960,
  `-130px` band, `ROW_SAME_ROW_MAX_DY=50px`). На `density=3.0` граница
  `y<320px` — это **другая физическая область** страницы (`<132dp` вместо
  `<139dp`) — гейт молча перестаёт срабатывать там, где должен, и там, где
  не должен: «Автогид» снова съезжает. Каждый новый дефект затыкался новой
  px-константой → новая дыра на другой плотности. Отсюда петля.
- «хардгард 211×64 @ y1120» в 2.25 = 93.8×28.4 @ y497.8dp. На другом
  телефоне те же dp дают другие px — тест по px-числам не проверяет правило.
- Снапшот фиксирует результат приложения при ТЕКУЩЕЙ плотности. Он не
  проверяет правило, и при каждом изменении правила его надо переснимать.

### Что это меняет в процессе (правила на сессию, до отмены)

1. **Ни одного нового px-гейта** (мораторий растёт плотностью: любые новые —
   в dp).
2. **Ни одного нового хардгарда по пикселям**: инвариант формулируется как
   `coverage(nodeDp) ≥ 2dp` или `pillCenterDp == nodeCenterDp ± 0.5dp`.
3. **Каждая правка `computeLayout` прогоняет `tools/density_sweep.py`**
   (8 плотностей, Δ ≤ 0.5dp на каждом узле-сигнале) — без этого не мержим.
4. **Снапшот — не аргумент.** Отчёт без «density sweep пройден» не
   принимается; золотые снапшоты остаются для A/B-сверки *поведения релиза*
   (было/стало на той же плотности), но не как инвариант плотности.
5. **Профиль важнее эвристики**: node с `viewId` описывается профилем;
   px-эвристика — только для узлов без id, список заморожен (гейты A–F
   сокращаются кадрами шага 4 — план не меняется, цель усиливается: после
   шага 4 каждый survivor должен проходить sweep).

### Инвариансный инструмент: `tools/density_sweep.py`

Вход: один дамп приложения (`pills.json` — a11y-ноды + RU text + `id` +
`est` + `sp` + `fsPx`; см. отклонение от ТЗ ниже). Метод (на каждый узел):
`px @2.25 → dp → px @density' ∈ {1.0, 1.5, 2.0, 2.25, 2.75, 3.0, 3.5, 4.0}
→ complete mirror `computeLayout` (полный порт: shape-классы,
ширина/высота, wrap/preview, ddx/ddy, band, (A)–(F), frame-1 profile
fall-through, row vertical guard) → dp` — сравнение выходов в dp между
плотностями.

**Требование (двойной порог):**
- `|Δ| ≤ 0.5dp` по ddx/ddy/ширина/высота/fs между плотностями;
- **flip** любого именованного px-условия (trail зеркала) — дефект даже
  при малом Δ («Автогид»-класс: гейт молча перестаёт срабатывать на
  другой плотности, не сдвинув пилюлю на этой).

**Шум-модель (отчёт честно, не скрывая):** вход синтез-устройства
квантован в integer px (`round(dp·d')`, пересчёт `sp`/`est` формулами
приложения от квантованной высоты). Даже идеально dp-чистый макет даёт до
~3px шума на выходе → Δ ≤ `0.5dp + 3px/d'` без flip = шум, не код
(отдельный счёт `noise-only`).

**Зеркало само проверяется (self-check @2.25):** обязано воспроизвести
наблюдаемые `pill[x,y,w,h]` из дампа (±2px). Отклонение > tol
классифицируется:
- `model-boundary[-approx]` — предел текстовой модели (смена строчности /
  один шрифтовой шаг; char-class-модель шрифтов оффлоун без TTF —
  задокументированное приближение, его пределы перечисляются, а не
  скрываются; такие пилюли исключаются из findings, не из отчёта);
- `port?` — настоящий дефект зеркала (вердикт PARTIAL, exit=2: такие
  узлы пока не выводимы — зеркало должно быть исправлено раньше).

**Реализация text-модели** (`tools/density_sweep_mir.py`, полный
байт-пอร์ต, float32 через struct): перенос = точный static layout
TextView (пробел налево, дефис через UAX#14) + `WRAP_CONTENT`-высота.
Ширина текста: per-text slope из самого дампа — `W(fs₀)=inner` на
однородных text-dominated пилюлях (S-пин) + интервальный L-пин для
обёртывающихся узлов (строка L в ширине W ⇒ `W₁∈((L−1)·A, L·A]`,
посредок поддиапазона, где зеркало даёт L строк); fallback —
char-class (α .50, цифра .57, пробел .30, пунктуация .44, CJK 1.0, «…»
.5). Сеть/шрифты недоступны (curl timeout, TTF нет) → задокументированное
приближение; Δ-сигнал остаётся про код.

**Состояние word_wrap на устройстве: OFF** (доказано геометрией дампа:
гейт (F) button-hug — пилюля == точный нода 368×102 «Конечно» (dialog
keyless) — достижим ТОЛЬКО в ветке `!multiline` (Java 1067–1121), и
baseline её содержит; двухсторонние строчки приходят из внутреннего wrap-
цикла приложения, который работает в !multiline тоже). Сессионная
пометка «ON» (10-21) ошибочна и заменена этим доказательством.

**frame-1:** self-check билда v2.10.44 (baseline дамп); cross-density и
список дефектов валидны для shipped v2.10.45 — v96↔v97 diff чист (6
ddx-only moves, `tools/_diff_v96_v97.py`), frame-1-ветка не добавляет
px-констант.

  `PILL-CHG` — пилюля сдвинулась **относительно своего узла** на >±2px,
  появилась или исчезла. «Относительно узла» — скролл приложения двигает
  узел и пилюлю вместе → это не дефект (проверено синтетическим тестом).

  узла до края пилюли (абсолютные углы): сдвиг позиции относительно узла на
  любой стороне = CHG, а чистое расширение ширины label-пилюли (растёт R)
  тоже = CHG — честное «изменились размер/покрытие», не артефакт формата
